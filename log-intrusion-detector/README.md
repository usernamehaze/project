# Log-Based Intrusion Detector

A rule-based intrusion detection tool for two real-world log formats: SSH
authentication logs (brute force, user enumeration, successful-login-after-
brute-force escalation) and web server access logs (path/admin scanning,
scanner user-agents, injection patterns, request-rate floods).

## Why this project

The [SMS phishing detector](../README.md) is supervised ML on text. The
[EXIF forensic analyzer](../exif-forensic-analyzer/README.md) is
feature-engineered forensics on images. This one is deliberately a third
technique — sliding-time-window, rule-based detection over event streams —
because that's the actual bread-and-butter of SOC/blue-team work: most
real intrusion detection isn't a trained model, it's "how many times did
this happen from this source in this window," done correctly and cheaply
enough to run on live traffic. Covering all three techniques (classification,
forensic feature engineering, and streaming rule-based detection) says more
about range than three variations on the same approach would.

## What it does

**Parsing** (`detector/parsers.py`) handles two SSH log formats, because
real deployments have both:
- **Legacy `pam_unix` syslog format**, as found in the real-world
  [Loghub](https://github.com/logpai/loghub) Linux dataset this project
  ships (`data/raw/linux_auth_sample.log` — 2,000 lines from a real,
  anonymized production server, used here under Loghub's terms for
  research/portfolio use, cited per their requirements).
- **Modern OpenSSH format** (`Failed password for ... from ... port ... ssh2`).

Plus web access logs in Common/Combined Log Format (Apache/Nginx).
Unparseable lines are counted, not silently dropped or treated as errors —
every report states a parse coverage percentage, because real logs always
contain a mix of formats/services a given parser doesn't target.

**SSH detection** (`detector/ssh_rules.py`), sliding 5-minute window by default:
- `brute_force_attempt` — 5+ failed logins from one source in the window
- `user_enumeration_scan` — 4+ *distinct* usernames tried from one source
  in the window (the real signal for enumeration, independent of whether
  any single username looks "invalid")
- `successful_login_after_brute_force` (**high** severity) — a source that
  was just brute-forcing succeeds afterward; the strongest signal in the
  rule set

**Web detection** (`detector/web_rules.py`):
- `path_scanning` — 15+ distinct paths returning 404 from one source
  within 60s (probing for admin panels/config files)
- `scanner_user_agent_detected` — request identifies as a named
  pentest/scanning tool (sqlmap, nikto, nmap, gobuster, ...) — deliberately
  *not* flagging generic curl/wget/python-requests, which are common and
  legitimate for health checks and API clients
- `injection_attempt_pattern` — SQL/XSS/path-traversal/JNDI patterns in
  the request path or query string
- `high_request_rate` — 50+ requests from one source within 10s

Both rule sets share one generic sliding-window primitive
(`detector/windowing.py`) rather than reimplementing the same logic twice.

## Verified results (real output, not illustrative)

**Real dataset** (`data/raw/linux_auth_sample.log`, 2,000 lines):
```
Lines parsed: 525/2000 (26.2% coverage)
Stats: total_events=525, failures=489, successes=36, successes_with_unknown_source=36
39 brute_force_attempt alerts (out of 47 distinct sources that had any failures)
```
The 26.2% parse coverage is expected, not a bug: the other lines are `su`
sessions, `check pass; user unknown` lines (redundant with the adjacent
failure line), and unrelated syslog noise this parser doesn't target.
39-of-47 sources crossing the threshold (not 47-of-47) shows the detector
is discriminating — 8 sources had a failure or two that never reached 5
within any 5-minute window, and correctly weren't flagged.

**Synthetic labeled fixtures** (`tests/fixtures/`, generated by
`scripts/generate_*_fixture.py`, ground truth in `tests/test_*.py`) — 26/26
tests pass:

| Scenario | Alert(s) raised |
|---|---|
| Benign logins/browsing, 1 typo-then-success, curl health-check | none |
| Rapid brute force ending in a successful login | `brute_force_attempt` + `successful_login_after_brute_force` |
| 10 distinct usernames tried, no success | `user_enumeration_scan` |
| 4 failures spread 8 minutes apart | **none** — see limitations |
| 20-path admin/config scan | `path_scanning` |
| sqlmap User-Agent | `scanner_user_agent_detected` |
| SQLi tautology + XSS + path traversal payloads | `injection_attempt_pattern` (all 3) |
| 60 requests in ~5s | `high_request_rate` |

## What didn't work (and why)

- **The web log parser silently dropped the exact request most worth
  catching.** The Combined Log Format regex captured the request path with
  `\S+` (non-whitespace), which is correct for well-formed requests but
  breaks the moment a request contains a literal, non-URL-encoded space —
  which is exactly what an SQL injection payload like `id=1' OR '1'='1`
  looks like when a scanning tool sends it unencoded. The line didn't error,
  it just failed to match the regex at all and was silently counted as an
  unparsed line — the SQLi attempt would have been invisible. Found via
  `test_analyze_log_web_auto` (parse coverage was 96/97, not 97/97) and
  `test_injection_patterns_detected` initially only finding 2 of 3 payloads.
  Fixed by making the path capture non-greedy and unanchored to whitespace
  (`.*?` up to the ` HTTP/x.x"` marker or closing quote) instead of `\S+`.
- **The real dataset can't support the escalation rule at all, and that's
  a property of the log format, not a parser bug.** In the legacy
  `pam_unix` format, `sshd(pam_unix)[PID]: session opened for user X by`
  lines carry no source IP — PAM session tracking in this format doesn't
  expose it, and the PID doesn't correlate back to the earlier
  `authentication failure ... rhost=` line for the same connection attempt
  (verified by checking: no PID from a `session opened` line ever appears
  in an `authentication failure` line in this dataset). So
  `successful_login_after_brute_force` structurally cannot fire on this
  real log, no matter how detection logic improves — it needs the modern
  OpenSSH format (or a richer log source) to work at all.
  `test_real_dataset_successes_have_no_known_source` pins this down instead
  of leaving it as an unexplained zero.
- **The user-enumeration alert's evidence is a partial snapshot, not the
  full scan**, because `find_bursts` alerts once, at the *first* moment a
  key crosses its threshold, then stops accumulating for that key. In the
  test fixture, an attacker tries 10 distinct usernames but the alert's
  evidence only lists 4 (the threshold) — not a bug, but a real interface
  wart: the alert underreports the true scope of an ongoing attack. Noted
  in `windowing.py`'s docstring and `test_user_enumeration_detected`
  asserts `>= 4`, not `== 10`, to keep the test honest about what the code
  actually does.

## Limitations

- **Fixed-window detection has a known blind spot: slow/low-and-slow
  attacks.** The synthetic fixture's `203.0.113.99` sends 4 failed logins
  8 minutes apart — never 5+ within any rolling 5-minute window — and is
  correctly *not* flagged by this detector (`test_slow_evasive_attack_is_not_detected`
  documents this on purpose). A real attacker who paces their attempts
  below the threshold evades every rule here. This is a fundamental
  limitation of fixed-window/fixed-threshold detection, not something a
  parameter tweak fixes — a production system would need longer-horizon
  statistical baselining (e.g. "this source's failure rate is anomalous
  for its history") on top of this.
- **Each source alerts at most once per rule** (see `windowing.py`) — a
  source that goes quiet and bursts again later won't re-alert. Fine for a
  single static log file; not fine for a live tailing deployment.
- **No IP reputation / geolocation.** A source hitting the brute-force
  threshold from a residential IP and from a known hosting/VPN range are
  treated identically; a real SOC tool would weight these very differently.
- **Injection-pattern matching is regex-based and will false-positive** on
  legitimate requests that happen to contain matching substrings (a search
  query that literally contains the text "union select", say) — it's a
  lead for a human to check, explicitly not a confirmed-attack verdict
  (the alert's own `note` field says this).
- The real-world dataset used here (Loghub's Linux sample) is from 2005-era
  production traffic; the attack *patterns* (SSH brute forcing) are still
  current, but the specific source IPs/hostnames are two decades old and
  tell you nothing about current threat infrastructure.

## Project structure

```
detector/parsers.py       SSH (legacy + modern) and web combined-log parsing
detector/windowing.py     generic sliding-time-window burst detection
detector/alerts.py        shared Alert type
detector/ssh_rules.py     brute force, user enumeration, escalation
detector/web_rules.py     path scanning, scanner UA, injection, rate flood
detector/engine.py        log-type auto-detection + orchestration
detector/cli.py           CLI entrypoint
data/raw/                 real Loghub Linux SSH auth log sample (2k lines)
scripts/generate_*.py     regenerate the labeled synthetic test fixtures
tests/                    26 pytest tests against fixtures AND the real dataset
```

## How to run

Pure Python standard library — no non-stdlib runtime dependencies.

```bash
pip install -r requirements.txt  # pytest only, for running tests

# regenerate the synthetic labeled fixtures (optional, already committed)
python3 scripts/generate_ssh_attack_fixture.py
python3 scripts/generate_web_log_fixture.py

# analyze a log (auto-detects SSH vs web)
python3 -m detector.cli data/raw/linux_auth_sample.log
python3 -m detector.cli tests/fixtures/web_attack_scenarios.log --json

# run tests
python3 -m pytest tests/ -v
```

## Future work

- Statistical/baseline anomaly detection (per-source historical failure
  rate) to catch the slow/low-and-slow attacks fixed-window rules miss.
- Allow a source to re-alert after a cooldown, for live-tailing a growing
  log rather than one-shot analysis of a static file.
- IP reputation/ASN lookups (offline dataset, to stay within this
  environment's no-internet constraint) to weight alerts by source type.
- Extend web rules to detect credential-stuffing against login forms
  specifically (repeated POSTs to a login endpoint with varying
  credentials), which is structurally similar to the SSH brute-force rule
  but currently only implemented for SSH.
