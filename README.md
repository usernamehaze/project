# Phishing / Smishing SMS Detector (with a Philippines-specific angle)

A text classifier that flags phishing/smishing SMS messages, combining a
general spam dataset with a hand-curated set of scam patterns that are
specific to the Philippines (GCash/PayMaya account-lock phishing, fake
courier COD fees, SIM registration scams, lotto/raffle scams, etc.).

## Why this project

Crime documentaries got me interested in how digital evidence and fraud
actually get investigated, and that pulled me toward cybersecurity and
digital forensics specifically, on top of a general interest in AI/ML. This
project sits at the intersection of both: it's a real ML classification
problem (feature engineering, model comparison, error analysis) applied to
a fraud/security use case I can evaluate critically rather than take on
faith.

The Philippines angle isn't decoration. Public spam datasets are almost all
UK/US English SMS, but the smishing that actually circulates here follows
different templates entirely — impersonating GCash/PayMaya, Globe/Smart,
local banks, LBC/J&T, and government agencies like the NTC, in Taglish. A
model trained only on the public dataset has never seen any of that.

## Dataset

- **[UCI SMS Spam Collection](https://archive.ics.uci.edu/dataset/228/sms+spam+collection)**
  (Tiago A. Almeida & José María Gómez Hidalgo, public/research use)
  — 5,574 labeled English SMS messages (`data/raw/sms_spam_collection.tsv`).
- **PH scam augmentation set** (`data/raw/ph_scam_augmentation.csv`,
  generated by `scripts/build_ph_augmentation_dataset.py`) — 95 messages
  (55 spam / 40 ham) I wrote from scratch, modeled on publicly reported
  scam formats (BSP/NTC/DICT consumer advisories, GCash's own scam-awareness
  posts, news coverage). No real phone numbers, accounts, or links — every
  message is synthetic. The ham half deliberately includes *legitimate-looking*
  GCash/bank notifications, so the model can't just learn "mentions GCash →
  spam"; it has to learn the actual signal (urgency + a link + a request for
  credentials, not just the brand name).

After combining and de-duplicating, the working dataset is **5,253 messages**
(13.3% spam) — still meaningfully imbalanced, which is why F1 on the spam
class (not accuracy) is the metric that matters here.

## Approach

**Features** (`src/features.py`):
- TF-IDF, word-level, 1-2 grams (10,269 features)
- TF-IDF, character-level, 3-5 grams (22,641 features) — catches obfuscated
  spelling (`fr33 l0ad`, spaced-out brand names) that word tokenization misses
- 12 handcrafted signals: has a URL / shortened URL, digit ratio, uppercase
  ratio, "SHOUTING" word count, exclamation count, money-amount mentions, PH
  phone number pattern, count of urgency phrases (`verify`, `suspended`,
  `claim now`, ...), count of PH-specific scam keywords (`gcash`, `otp`,
  `ntc`, `j&t`, ...)

**Models compared** via 5-fold stratified cross-validation on the training
split (`src/train.py`), scored on F1 for the spam class:

| Model | CV F1 (spam) |
|---|---|
| Naive Bayes | 0.941 |
| **Logistic Regression** | **0.949** |
| Linear SVM | 0.943 |

Logistic Regression won and was refit on the full training set (80/20
stratified split, seed 42).

**Held-out test set** (1,051 messages, never seen during training or model
selection):

| | precision | recall | f1 |
|---|---|---|---|
| ham | 0.996 | 0.998 | 0.997 |
| spam | 0.985 | 0.971 | 0.978 |

Confusion matrix: **TN=910, FP=2, FN=4, TP=135** — 2 legitimate messages
flagged as spam, 4 phishing/spam messages missed, out of 1,051.

Run `python -m src.evaluate` to reproduce this and see the actual
misclassified messages, not just the numbers.

## What didn't work (and why)

- **Naive Bayes collapsed to F1 = 0.168** the first time I combined TF-IDF
  with the handcrafted features, despite doing fine (F1 = 0.82) on TF-IDF
  alone. MultinomialNB assumes count-like features on a roughly consistent
  scale; mixing in raw, unbounded values like message `length` (up to ~500)
  alongside 0-1-ish TF-IDF weights violates that assumption outright and
  wrecks its probability estimates.
- **LinearSVC failed to converge** (`ConvergenceWarning`) even at
  `max_iter=5000`, for the same underlying reason — a few large-magnitude
  handcrafted features dominated the optimization landscape.
- **Fix**: `MaxAbsScaler` on the full concatenated feature matrix (train-fit,
  applied to test) before any model sees it. This is sparsity-preserving
  (unlike `StandardScaler`, which would densify a 32,922-column sparse
  matrix and blow up memory). After scaling: Naive Bayes jumped to F1 = 0.941,
  and LinearSVC converged cleanly. Lesson: feature scale matters even for
  "just concatenate the features" pipelines, and it's easy to miss when
  each feature type looks fine in isolation.
- **A "false negative" that probably isn't the model's fault**: one missed
  spam message — *"Sorry I missed your call let's talk when you have the
  time. I'm on 0709..."* — reads exactly like an ordinary text and got
  P(spam) = 0.02. It's a UCI-labeled premium-rate callback scam (a
  follow-up text after a subscription trap), which is a genuinely hard
  case — even a human reading it cold wouldn't flag it without the earlier
  message in the thread. This is a labeling/context limitation of the
  dataset, not something more feature engineering fixes.
- Encouragingly, **none of the 6 test-set errors came from the PH
  augmentation set** — all were UCI messages. That's a reasonable signal
  the PH-specific keyword/urgency features are pulling their weight, though
  with only 95 PH-augmented examples total this isn't a strong claim.

## Limitations

- The PH augmentation set (95 messages) is synthetic and hand-written by
  me, not sourced from real, consenting victims' inboxes — it encodes
  publicly known scam *templates*, not validated real-world traffic. Real
  smishing evolves fast; this will go stale.
- English/Taglish only, written in Latin script — no pure Tagalog, no
  code-switched messages using non-standard spelling variants beyond what's
  in the augmentation set.
- Trained on a fairly small, imbalanced dataset (5,253 messages, 13.3%
  spam). Precision/recall at this scale can be noisy — the CV standard
  deviations (±0.01-0.02 F1) reflect that.
- This is a portfolio/educational project, not a production fraud filter.
  It has no rate limiting, no adversarial robustness testing, and hasn't
  been evaluated against an attacker deliberately trying to evade it.

## Project structure

```
data/raw/                          UCI dataset + PH augmentation CSV
scripts/build_ph_augmentation_dataset.py   regenerates the PH CSV
src/data_loader.py                 load + combine + split datasets
src/features.py                    TF-IDF + handcrafted feature extraction
src/train.py                       CV model comparison, fit best, save artifacts
src/evaluate.py                    metrics + false positive/negative analysis
src/predict.py                     CLI: classify one message, explain why
models/                            saved vectorizers/scaler/model (joblib) + metadata.json
results/                           metrics.json, test_predictions.csv
tests/                             pytest unit + integration tests
```

## How to run

```bash
pip install -r requirements.txt

# regenerate the PH dataset (optional, already committed)
python3 scripts/build_ph_augmentation_dataset.py

# train + compare models, save the best one
python3 -m src.train

# evaluate on the held-out test set + see misclassified examples
python3 -m src.evaluate

# classify a message
python3 -m src.predict "GCash Alert: Your account will be suspended, verify now: bit.ly/xyz"

# run tests
python3 -m pytest tests/ -v
```

## Future work

- Expand the PH augmentation set with more scam categories and dialectal
  variation (Cebuano, Ilocano code-switching).
- Try a lightweight transformer (e.g. distilled multilingual BERT) and
  compare against the TF-IDF baseline on the same test set — the honest
  question is whether it's actually worth the added complexity/latency
  here, given how well the linear model already does.
- Basic adversarial testing: how much can a spam message be reworded before
  it slips past the classifier?
